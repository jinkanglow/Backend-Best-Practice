# Authorization and Idempotency: Behavioral Verification Contract

## Authorization negative test

Preconditions: two distinct credentials representing different principals or tenants; one resource owned by principal A; isolated test service; explicit expected denial status. Execute the same resource read with A and B. A must receive the configured success status; B must receive 401, 403 or 404 as configured. A failure indicates a concrete violation for that fixture, not a universal authorization defect. A pass establishes only that particular resource/identity pair. Never print tokens or full response bodies.

## Idempotency concurrency test

Preconditions: isolated mutable test state; a dedicated read-only endpoint reporting a numeric count of committed business side effects; identical idempotency key for all concurrent requests; the test owner has authorized writes. Capture count before, dispatch 2–12 concurrent requests, capture count after. Require observed delta equal to configured expected delta (normally one) and statuses within an explicitly allowed set. A successful response comparison without the side-effect probe is insufficient. The test must reset state between runs; the harness does not reset it. Unique keys must be generated by the test setup, not reused across test runs.

## Boundaries

Only loopback HTTP destinations are permitted. Credentials are loaded from environment variable names, not embedded in manifests or reports. No redirects are followed. Network errors fail the observation. This is not crash recovery, distributed linearizability verification, authentication assurance, or independent evidence attestation. Local observations must not be promoted to full control compliance. Use a protected CI runner and separate trust boundary for attestation.
